# 写入硬件边界与本轮优化（2026-11-14）

## 结论

当前写入离 SSD 的大块带宽很远，但小批量事务首先受到同步提交延迟限制。大维度请求另外存在明显的 JSONL/SQL 读取与解析开销。本轮保留每次提交的两次同步，通过输入缓冲和连续字符串扫描提速，没有关闭 WAL、校验和或同步落盘。

同一批预生成 JSONL、相同批大小、同一块 SSD、每种三次平均：

| 数据与批量 | 修改前 INSERT | 修改后 INSERT | 吞吐提升 | 修改后引擎 CPU 时间 |
|---|---:|---:|---:|---:|
| 10,000 行 × 128 维，B100 | 0.797941 s | 0.604412 s | 1.32× | 0.150 s |
| 4,096 行 × 1024 维，B256 | 0.872792 s | 0.264739 s | 3.30× | 0.180 s |
| 10,000 行 × 128 维，B1024 | 未测同批量修改前 | 0.141261 s | 相对修改后 B100 为 4.28×，属于批量收益 | 0.083 s |

“修改前”是新实现的 `b63ed07` 对应二进制，不是旧项目。此表比较的是持久化 INSERT 请求从发送到收到成功响应的时间，包含管道传输、JSONL/SQL 解析、存储与标量索引更新、WAL 和向量文件同步。每一请求实际对应一批，未暗中拆批。

数据为 4 列的公开规模形状：id、category、content、embedding；向量为固定种子的随机样本。空表上先执行 CREATE VECTOR INDEX，但该实现此时尚无可训练样本，因此这里不包含已训练 IVF/PQ 的逐条维护成本。8 列配置另用于批量恢复验证。本轮不是 100k/300k 全套比赛实验。

## 计时口径修正

之前报告的 1.304 秒包含 Python 格式化向量、拼接 SQL 和 JSON 编码。旧比较脚本直接调用 Python Database，新比较脚本走 C++ JSONL，且查询种子也不完全相同；因此之前的“同口径 23.3×/3.5×”不能作为严格的新旧 C++ 比值，也不能把写入差异直接归因于元信息持久化。

本轮预先生成完整请求，比较前后请求 SHA-256 一致。生成耗时单列：128 维约 0.55–0.61 秒，1024 维约 1.82–1.89 秒。正常关闭时的 checkpoint 同样单列，未计入 INSERT 时间，也未从报告中省略：

| 负载 | 修改后 INSERT | checkpoint | 两者合计 |
|---|---:|---:|---:|
| 10k/128/B100 | 0.604412 s | 0.063176 s | 0.667587 s |
| 4096/1024/B256 | 0.264739 s | 0.051615 s | 0.316354 s |
| 10k/128/B1024 | 0.141261 s | 0.061929 s | 0.203190 s |

DDL/ready、数据生成和独立检查均另计。实验未设置 CPU 亲和性或 Docker 资源限制；引擎仍为单执行线程。

## 硬件实测

CPU 为双路 Intel Xeon Gold 6430。工作目录 `/mnt/SSD1/zzp/seekdb-round2-lite2000/` 对应 `/dev/nvme1n1`，ext4，TiPlus7100 2TB，测试时约 75% 使用率。此前 `/tmp` 位于另一块 NVMe 的系统逻辑卷，不是 SSD1。

[厂商 TiPlus7100 参数](https://www.ymtc.com/cn/products/43.html?cat=44)列出 2TB 顺序写入最高 6000 MB/s。这是厂商特定条件下的峰值，不是数据库事务吞吐保证。

所有硬件测试只创建 `zzp` 新实验目录中的普通文件，写完 fdatasync，再关闭并删除该测试文件。没有裸盘写入、全盘清缓存或修改挂载参数。

| 路径与方法 | 结果 | 次数 |
|---|---:|---:|
| SSD1，2 GiB，1 MiB 请求，O_DIRECT 单路，末尾 fdatasync | 平均 4891.68 MB/s，范围 4421.14–5196.60 | 3 |
| SSD1，同样数据，4 个并发写入流 | 平均 4279.81 MB/s | 3 |
| SSD1，buffered 顺序写入并等待末尾 fdatasync | 平均 2392.99 MB/s | 3 |
| HDD2，256 MiB，O_DIRECT 单路并同步 | 130.18 MB/s | 1 |

以上是当前文件系统、盘占用率及短时工作负载下的参考带宽；2 GiB 测试没有测出耗尽 SSD 内部缓存后的持续速度，也不构成硬件绝对极限。

## 从带宽换算时间

只计算 float32 原始向量，按实测 4891.68 MB/s：

| 数据 | 向量字节数 | 纯传输时间 |
|---|---:|---:|
| 10,000 × 128 | 5,120,000 B | 1.05 ms |
| 100,000 × 1024 | 409,600,000 B | 83.7 ms |
| 300,000 × 1024 | 1,228,800,000 B | 251 ms |

这只是一份原始向量的带宽换算，不包含 SQL 文本、WAL、标量字段、文件系统放大、解析、索引、提交屏障或 checkpoint，不能当作完整数据库的可达时间。

更适合当前设计的参照是：每批写入向量并同步，再写 WAL 并同步。独立 C++ 微基准每行模拟 128 字节 WAL，未执行数据库解析和索引操作：

| 负载 | 仅两文件写入与同步 | 平均每提交 | 当前完整 INSERT |
|---|---:|---:|---:|
| SSD1，500 行，128 维，S1 | 1.974 s | 3.95 ms | 未在本轮测完整 S1 |
| SSD1，10k/128/B100 | 0.404893 s | 4.05 ms | 0.604412 s |
| SSD1，4096/1024/B256 | 0.080258 s | 5.02 ms | 0.264739 s |
| SSD1，10k/128/B1024 | 0.052002 s | 5.20 ms | 0.141261 s |
| HDD2，10k/128/B100 | 3.50239 s | 35.02 ms | 未在本轮测完整 HDD INSERT |

以 `T >= max(物理写入字节 / 带宽, 提交次数 × 每次同步提交延迟)` 估算下界。真实同步延迟随大小、文件增长、盘状态变化，上表应看作同形状 I/O 的实测参照，不能逐项精确相减作为 CPU 分解。

128 维 B100 当前达到该提交模型吞吐的约 67%；1024 维 B256 约 30%。这不是 SSD 带宽利用率。小批次已明显受同步延迟限制；高维 SQL 路径仍有较大的 CPU 优化空间。

B100 在两版中均写出 5,120,000 字节向量和 776,112 字节 WAL，Linux 进程 I/O 计数中的 write_bytes 为 6,504,448 字节。B256 的文件字节数也相同。一次额外 `strace -c -w` 诊断记录 205 次 fdatasync、累计约 0.459 秒（包括 DDL、收尾；带跟踪开销，未混入三次正式计时）。

## 落地的改动与验证

1. C++ 输入关闭与 C stdio 的隐式同步，并解除 cin 的自动输出流绑定。JSONL 响应仍显式 flush。
2. JSON/SQL 引号内的连续无转义字符串按段复制，保留转义处理，减少逐字符追加和分配。
3. WAL 解码以实际载荷长度约束 token 数，替换固定 4096 上限。原来的 8 列 B256 已提交请求可被该上限错误拒绝。
4. STATE v3 保存 checkpoint 对应的向量文件边界。恢复从该边界（无 STATE 时为 0）重放，拒绝已提交向量缺失，并截断未提交尾部。原实现错误地从崩溃时文件末尾开始重放。

当前运行时代码为 **2175 个物理行**；原 2000 行检查仍报告超出，按用户已放宽的要求如实记录。独立测量和测试代码不计入运行时代码。

- 当前公开协议：20/20。
- 字符串扫描：2000 个包含转义、引号和 UTF-8 的案例通过。
- 20 次强杀恢复：同时检查已提交行、未提交行排除和非零向量距离，20/20。
- 8 列 B256/B1024：无 checkpoint 与已有 checkpoint（含删除过的向量尾部）各一例，4/4；重启后检查全部 ID 和非零向量距离。
- 修改前的 B256 恢复失败日志保留。先解除 token 上限后暴露向量偏移问题，随后修复；没有把这些失败计为通过。

兼容性边界：旧 STATE v2/JSON 在 WAL 为空时可读取并升级；旧格式没有保存可靠的向量重放边界，因此带非空 WAL 时明确报错，不猜测偏移或静默加载。测试目录均隔离，未迁移原有业务数据。

这些是进程强杀检查，不等同于物理断电验证。更完整的故障矩阵仍属于原计划未完成项。

## 下一步优化优先级

先继续减少协议扫描、浮点解析、字符串复制和每次提交重复扫描 MemTable 的 CPU 成本。批量 INSERT/事务可以显著摊薄提交次数，但只能在比赛请求契约允许时使用，并单列批量大小。

要进一步降低每事务的约 4–5 ms 同步代价，需要重新设计可完整恢复向量的单 WAL 提交路径，或在请求并发允许时进行 group commit。这属于新的持久化设计与故障验证工作；本轮没有通过省略同步实现该收益。
