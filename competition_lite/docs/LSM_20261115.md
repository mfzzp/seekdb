# LSM 主读与恢复改造：2026-11-15

本轮把 SST 接入实际读取和恢复，完成可溢写的事务写集、持久二级键、流式分层合并、Manifest/WAL 代际发布和向量 GC，并保留有容量上限的 exact 热表路径。128 MiB 无 swap 容器通过了 15 万行、约 398 MiB 数据的提交、查询和恢复。

性能有取舍：相对约 2k 分的 f885c28，最终三轮中位数为查询请求耗时 **下降 14.31%**、容器峰值 **下降 17.06%**，写入耗时 **增加 16.35%**。相对 ce497c6，分别为 -3.13%、-24.69%、+15.45%。累计写入诊断也增加，不能称为综合成绩已提高，更不能推算官方 5000 分。

## 交付边界和源码一致性

- SST 成为正常主读/恢复来源，STATE 仅用于旧 Lite 格式导入；正常 checkpoint 不再保存整表。
- BEGIN 和语句回滚改为私有写集，无整表复制；大事务可溢写，按大小分组归并。
- 每键保留最后版本；行采用长度编码，修正旧 SST 最后一个普通字段遗漏和分隔符歧义。
- 新 SST、Manifest、WAL、向量代际均按“先持久发布，再回收”处理；读视图引用保住旧 SST。
- 仍是单写者、同步 compaction；没有后台合并、多客户端 MVCC 或近似 ANN。冷表超大结果物化会明确报资源上限，需要 LIMIT。详见 [实现说明](IMPLEMENTATION.md)。

最终镜像从 **Git 暂存对象的原始字节** 导出构建，未用 Windows 换行副本替代。Dockerfile 与 .dockerignore 一并来自该 Git 输入。运行时两文件共 **1627 物理行**，包含头文件、注释和空行，低于原定 2000 行；删除了不再使用的旧存储和 PQ 路径。

## 六组指标的测量边界

服务器 Xeon Gold 6430；镜像内 Debian GCC 12.2，`-O3 -DNDEBUG -std=c++17 -Wall -Wextra`。常规对照统一 2 CPU、2 GiB、swap=0，引擎固定 CPU 0、1；驱动和真值在容器外。每轮新建数据库，三个版本及 Block 轮换顺序、串行执行，各三轮。

与 ce497c6 上轮使用同一份预编码输入：1 万行、128 维、1000 exact 查询、K=10，一半 category 等值过滤，固定 B100、100 次持久提交。输入哈希见 [prepared](../results/lsm_20261115/prepared10k/prepared.json)。它是公开参数形状的自建负载，不是官方评分器。

请求计时包含 JSONL 发送、完整响应和客户端解析；生成数据、真值及事后校验不计入。查询整体区间还含驱动生成 SQL 的时间，单独列出。18 次预热含首次缓存构建，单列而非隐藏。索引、checkpoint 和重启另计。诊断二进制与最终计时分开。

## 超内存验收

最终镜像使用 128 MiB、2 CPU、swap=0，关闭热表缓存，MemTable 1 MiB、SST 2 MiB、mmap 8 MiB。宿主驱动生成 15 万行：每行 1024 字符 payload、128 维向量及尾字段；整个装载是一个显式大事务，测试写集溢写。主行负载保守下界 159000000 bytes 已大于内存限额，最终文件 417146266 bytes（约 398 MiB）。

装载到持久提交约 19.789 s，包含宿主生成并发送容量测试请求的时间；它不是预编码 B100 的性能计时。查询时进程 VmHWM 27408 KiB，容器峰值达到 128 MiB 限额但无 OOM、无 swap。重启约 0.197 s（含 docker 启动）；全域及范围 exact 与独立公式真值一致，抽取完整行向量核对一致。此处大事务与 B100 性能负载不同，不能把它的吞吐量当作 B100 提升。证据见 [容量结果](../results/lsm_20261115/capacity-release/result.json)。

所有最终结果集中在 [six-metrics.json](../results/lsm_20261115/six-metrics.json)，逐请求原始记录压缩保存在 `paired-release-queries.jsonl.gz` 和 `selectivity-release-queries.jsonl.gz`。同步日志、输入/源码哈希、未通过的初始 sanitizer 记录与最终通过记录均保留，可复查而非仅保留结论。
